# End-to-End TPS — Design Spec

- **Status:** COMPLETE — shipped 2026-10-24 (migration `0018`, Worker `fd9038b9`)
- **Date:** 2026-10-24
- **Scope:** benchmark metric, D1 schema, aggregation, API, leaderboard/compare/model-detail UI, methodology
- **Decision owner:** user (design decisions approved 2026-10-24)

## 1. Problem

The dashboard shows one unqualified "TPS" number. That number is decode-only:
`output_tokens / (completed_at - first_token_at)`. It excludes TTFT, network,
and queueing. For normal token streams it is a useful decode rate. For models
that deliver tokens in large blocks it is not a per-token rate at all, and the
leaderboard currently ranks it as if it were.

Evidence from the deployed system (2026-10-23/24):

- `compare=38,34,69` showed **2,129.8 TPS** for NVIDIA
  `google/diffusiongemma-26b-a4b-it`.
- All **514/514** SUCCESS runs for that model have exactly **2 chunks**. The
  screenshot run was 279 tokens, 472 ms TTFT, 131 ms generation: two content
  chunks separated by 131 ms. The 2,129.8 figure is 279 tokens divided by one
  inter-block gap.
- The two Groq rows are genuine decode throughput: ~370 chunks per run, median
  decode 1,062–1,155 TPS, median end-to-end 527–625 TPS.
- `/api/compare` used `AVG(tps)` while `/api/leaderboard` used medians, so the
  same model/window read **1,085 TPS via compare** and **699 TPS via
  leaderboard**.
- The latest-run overlay (`tps_now`) is a single run, so one outlier becomes a
  headline: 341 tokens / 0 ms after 83 s TTFT produced **17,050 TPS**.
- Independent references put Groq `gpt-oss-20b` near 900–1,000 TPS decode, not
  the 229 P50 shown by OpenRouter's rolling production metric. NVIDIA's
  DiffusionGemma claim of 1,100+ TPS is block throughput, not per-token decode.

The product problem is not that the decode formula is wrong. It is that one
number is being used for two different questions:

1. "How fast does this model emit tokens once it starts?" → decode.
2. "How fast does a whole request finish?" → end-to-end.

## 2. Goals and non-goals

### Goals

- Show both throughput metrics, explicitly labeled, on the leaderboard, compare
  panel, model detail, dashboard summary, and methodology.
- Make **end-to-end TPS** the metric that drives Overall Score, the "Fastest"
  sort, the fastest recommendation card, and compare's winner.
- Flag block-delivery models so a high decode number is not read as per-token
  speed.
- Carry the new metric through the real pipeline: per-run storage → hourly and
  10-minute aggregates → leaderboard snapshot → API → UI.
- Keep every existing API field and behavior backward compatible.

### Non-goals

- Changing the decode formula or its 20 ms floor.
- Re-running historical benchmark probes.
- Splitting TTFT into network, queue, and provider-compute components.
- Replacing `tps_now` with a rolling median (existing latest-run semantics stay).
- Changing scoring profile weights or adding new profiles.
- Adding end-to-end to `daily_model_stats` (long-range daily views keep decode;
  they are outside the 7-day product window).

## 3. Definitions

Let:

- `S` = `request_started_at` (stamped before `fetch`, `engine.ts:120`)
- `F` = `first_token_at` (first SSE chunk with content)
- `C` = `request_completed_at`
- `N` = visible output tokens (same numerator for both metrics; provider
  `usage.completion_tokens` when present, char/4 heuristic otherwise)

Then:

```
decode_tps = N / (max(20, C_ms - F_ms) / 1000)      # existing `tps` baseline
e2e_tps    = N / ((C_ms - S_ms) / 1000)             # new
```

Rules:

- `e2e_tps` is stored only when `status = 'SUCCESS'`, `N > 0`, `S` and `C` are
  present, and `C_ms > S_ms`. Otherwise null.
- No 20 ms floor, no clamping, no upper bound on `e2e_tps`. A genuinely fast
  request reports its real rate.
- Stored rounded to two decimals.
- `decode_tps` behavior is unchanged, including the 20 ms floor and the hybrid
  inter-token/wall-clock method.
- `e2e_tps` includes connection setup, queueing, network, TTFT, and decode. It
  is the user-perceived rate **from this observatory's Cloudflare runner**, not
  a universal provider guarantee.
- Block delivery is informational: `median_chunks_7d < 8` with at least
  `MIN_SAMPLES.w7d` (5) SUCCESS samples. It never changes a number or a rank.

Worked example (the screenshot run):

| Metric | Calculation | Result |
|---|---|---|
| Decode | `279 / 0.131` | **2,129.8 TPS** |
| End-to-end | `279 / (0.472 + 0.131)` | **462.7 TPS** |

Using the stored start/completion timestamps may differ by a few milliseconds
from `ttft + generation`, which is expected and harmless.

### Convention alignment

`CONVENTIONS.md` line 58 currently says "Never use total duration for TPS; MUST
use generation_time = completed_at - first_token_at." That rule stays true for
the field named `tps`: decode TPS is still generation-window only and is never
computed from total duration.

`e2e_tps` is a **different metric with a different name**. It is never written
into `tps`, never displayed as plain "TPS", and never used to describe
token-generation speed. The implementation must update `CONVENTIONS.md` to
state both rules explicitly:

- `tps` / Decode TPS = generation window only (existing prohibition stands).
- `e2e_tps` / End-to-end TPS = whole request, separately labeled, and the only
  throughput metric used for ranking.

This prevents a future contributor from "fixing" e2e back into `tps` or from
citing the old rule to remove the new metric.

## 4. Ranking policy

End-to-end is the only throughput metric that ranks.

- **Overall Score speed input:** `e2e_tps_7d ?? e2e_tps_24h ?? e2e_tps_now`.
  Profile weights are unchanged (`balanced` 0.40, `fastest` 0.60, `latency`
  0.20, `reliable` 0.20, `coding` 0.35 for the `tps` slot).
- **Consistency:** `min(e2e_now, e2e_7d) / max(e2e_now, e2e_7d)`.
- **Score gate:** a row needs at least one non-null e2e window. A row with only
  decode values gets `overall_score: null` and is listed unranked.
- **Rank gate:** `assignRanks` gates on the e2e fields when present, falling
  back to the legacy decode fields only for fixtures that predate this metric.
  The existing 24h sample and latest-status gates are unchanged.
- **`sort=tps`:** resolves to `e2e_tps_7d ?? e2e_tps_24h ?? e2e_tps_now`
  (today it skips the 24h fallback; the new chain includes it).
- **`fastest_now`, `best_tps`, `best_consistency`:** use e2e.
- **Compare winner:** highest `e2e_tps_7d`.
- **Decode never ranks.** It remains visible for diagnosing decode behavior and
  for block-delivery awareness.

Expected rank movement is intentional and must be documented: block-delivery
models drop sharply once end-to-end is the speed input, and some high-TTFT
models drop relative to low-TTFT models with similar decode rates.

## 5. Data model

### Migration `migrations/0018_e2e_tps.sql`

Additive only. No table rebuilds, no CHECK changes, no new indexes (all reads
are already keyed by model/window).

```sql
ALTER TABLE benchmark_runs ADD COLUMN e2e_tps REAL;

UPDATE benchmark_runs
SET e2e_tps = ROUND(
  output_tokens * 1000.0 /
  ((julianday(completed_at) - julianday(started_at)) * 86400000.0), 2)
WHERE status = 'SUCCESS'
  AND output_tokens > 0
  AND started_at IS NOT NULL
  AND completed_at IS NOT NULL
  AND julianday(completed_at) > julianday(started_at);

ALTER TABLE hourly_model_stats ADD COLUMN median_e2e_tps REAL;
ALTER TABLE tenmin_model_stats ADD COLUMN median_e2e_tps REAL;

ALTER TABLE leaderboard_snapshot ADD COLUMN e2e_tps_1h REAL;
ALTER TABLE leaderboard_snapshot ADD COLUMN e2e_tps_24h REAL;
ALTER TABLE leaderboard_snapshot ADD COLUMN e2e_tps_7d REAL;
ALTER TABLE leaderboard_snapshot ADD COLUMN median_chunks_7d REAL;
```

Backfill correctness is verified before deployment on a seeded local D1: for a
sample of SUCCESS rows, the SQL value must equal the JS formula within 0.01
TPS. After migration, this query must return `0`:

```sql
SELECT COUNT(*) FROM benchmark_runs
WHERE status = 'SUCCESS' AND output_tokens > 0
  AND completed_at IS NOT NULL AND started_at IS NOT NULL
  AND julianday(completed_at) > julianday(started_at)
  AND e2e_tps IS NULL;
```

If `julianday` parsing disagrees with JS on the sample, the fallback is a
bounded admin backfill (Section 9) that writes e2e from JS, not a fabricated
SQL value. No row is ever given an e2e value without a real duration and token
count. A second check distinguishes a genuine zero from a parse failure:

```sql
SELECT COUNT(*) FROM benchmark_runs
WHERE status = 'SUCCESS' AND output_tokens > 0
  AND started_at IS NOT NULL AND completed_at IS NOT NULL
  AND (julianday(started_at) IS NULL OR julianday(completed_at) IS NULL);
```

That count must also be `0`.

Retention is unchanged: raw runs 7–14 days, 10-minute and hourly aggregates
30–90 days, snapshot refreshed hourly.

## 6. Write path

### `src/benchmark/engine.ts`

`finalize()` computes `e2e_tps` from the same `startedMs` and `completedMs`
values that become the stored ISO timestamps, so new writes and the migration
backfill agree:

```ts
const elapsedMs = completedMs != null ? completedMs - startedMs : null;
const e2eTps =
  status === "SUCCESS" && outputTokens != null && outputTokens > 0 &&
  elapsedMs != null && elapsedMs > 0
    ? Math.round((outputTokens * 1000 * 100) / elapsedMs) / 100
    : null;
```

Added to `BenchmarkResult` as `e2e_tps: number | null`.

### `src/db/queries.ts` — `insertBenchmarkRun`

- Add `e2e_tps` to the primary INSERT column list and bind array.
- Add `e2e: r.e2e_tps` to the `last_now_json` entry.
- Keep the existing fallback ladder: primary → insert-only with `tps_method` →
  method-less insert. The oldest method-less fallback omits `e2e_tps` so a
  pre-0018 database still accepts the row. The migration/backfill repairs any
  null created in that window.

### `src/db/snapshot.ts` — `NowEntry`

Add `e2e: number | null`. `nowFor()` returns it unchanged. `last_now_json`
entries written before the deploy simply lack the field; readers use
`entry?.e2e ?? null`.

## 7. Aggregation

### Hourly and 10-minute (`src/db/queries.ts`, `aggregateWindow`)

- Select `GROUP_CONCAT(e2e_tps) as e2e_tpss`.
- Parse with `parseConcatNumbers`, filter like the decode list (non-null; zero is
  a real measurement), compute `median_e2e_tps = percentile(e2e, 50)`.
- Write `median_e2e_tps` in the same `INSERT OR REPLACE`. The function is
  shared by `computeHourlyAggregates` and `computeTenminAggregates`, so both
  tables gain the value from one change.
- `request_count` continues to count all runs, including failures. The median
  list contains only measurable successes, matching decode behavior.

### Snapshot (`src/db/snapshot.ts`)

The existing single raw `GROUP_CONCAT` pass gains:

```sql
GROUP_CONCAT(CASE WHEN started_at >= ? THEN e2e_tps END) as g_e2e_1h,
GROUP_CONCAT(CASE WHEN started_at >= ? THEN e2e_tps END) as g_e2e_24h,
GROUP_CONCAT(CASE WHEN started_at >= ? THEN e2e_tps END) as g_e2e_7d,
GROUP_CONCAT(CASE WHEN status='SUCCESS' THEN chunk_count END) as g_chunks_7d
```

`SnapshotRaw` gains the four strings. `mergedRaw()` concatenates them across
benchmark types for the `all` view, exactly as it already does for decode.
`SnapshotRow` and `buildSnapshotRows()` gain:

- `e2e_tps_1h` gated by `MIN_SAMPLES.w1h`
- `e2e_tps_24h` gated by `MIN_SAMPLES.w24h`
- `e2e_tps_7d` gated by `MIN_SAMPLES.w7d`
- `median_chunks_7d` gated by `MIN_SAMPLES.w7d` **on the SUCCESS count**
  (`ok_7d`), because `chunk_count` is only meaningful for SUCCESS runs

The upsert column list, values, and `ON CONFLICT DO UPDATE SET` clause add all
four fields. No extra query is introduced.

### History (`src/api/history.ts`)

- Aggregated paths select `AVG(median_e2e_tps) as median_e2e_tps` (or the plain
  column for a single benchmark type).
- Raw fallback selects `e2e_tps as median_e2e_tps`.
- `HistoryPoint` gains `median_e2e_tps: number | null`.
- Existing hourly rows without the backfill return null for this field; Recharts
  shows a gap until the hour is recomputed. No interpolation or fabrication.

### Compare (`src/api/compare.ts`)

Compare reads the precomputed `leaderboard_snapshot` first, for
`benchmark = 'all'` and the requested model ids, so it reports the same
medians as the leaderboard:

- `tps_24h`, `tps_7d` = decode snapshot values
- `e2e_tps_24h`, `e2e_tps_7d` = end-to-end snapshot values
- `ttft_24h`, `ttft_7d`, `uptime_7d`, `error_rate` from the same row

If a model has no snapshot row, fall back to raw-run medians parsed from
`GROUP_CONCAT(e2e_tps)` and `GROUP_CONCAT(tps)`. Never fall back to `AVG` for a
median field. `recommended_provider` sorts by `e2e_tps_7d`. The edge cache key
gains `&v=2` so a pre-deploy cached response without e2e cannot be served after
the upgrade for up to 300 s.

### Leaderboard live fallback (`src/api/leaderboard.ts`)

When the snapshot is empty or unavailable, the existing live-query path must
produce the same fields from raw runs: e2e medians for 1h/24h/7d and
`median_chunks_7d`, gated by the same `MIN_SAMPLES` values. The `tps_now`
overlay path also exposes `e2e_tps_now`. No field is null solely because the
snapshot was unavailable.

## 8. API contract

All field names are unchanged. Existing decode fields keep their exact meaning.
Two existing behaviors change deliberately and are documented: `best_tps` now
selects the end-to-end leader, and `sort=tps` now orders by end-to-end.

### `LeaderboardRow`

| Field | Type | Meaning |
|---|---|---|
| `tps_now/1h/24h/7d` | `number \| null` | decode, unchanged |
| `e2e_tps_now/1h/24h/7d` | `number \| null` | end-to-end |
| `median_chunks_7d` | `number \| null` | median content chunks per SUCCESS run |

`tps_now` and `e2e_tps_now` both come from the latest-run overlay. An old
overlay entry yields `e2e_tps_now: null`, not a fabricated value.

### `/api/compare`

Each row adds `e2e_tps_24h` and `e2e_tps_7d`, keeps `tps_24h`/`tps_7d` as
decode, and keeps `ttft_24h`/`ttft_7d`, `uptime_7d`, `error_rate`.
`recommended_provider` is now based on end-to-end.

### `/api/history`

Each point adds `median_e2e_tps`. `median_tps` remains decode.

### Leaderboard response `summary` block

`best_tps` keeps its key but now selects the end-to-end leader and is an alias
of the new explicit `best_e2e_tps` row. The UI reads `best_e2e_tps.e2e_tps_now`
for the headline and `best_e2e_tps.tps_now` for the decode sub-line. No
`best_decode_tps` row is added because the same row already carries decode.

### OpenAPI

Document both metrics, the null rules, the ranking policy, and the block-delivery
field. The existing `/api/leaderboard` description that says "TPS" must state
"decode" and point to `e2e_tps_*` as the ranked metric.

## 9. Operations and backfill

### Deploy order

1. Apply `0018_e2e_tps.sql` to remote D1 (`npm run migrate`).
2. Build the frontend (`vite build`) and deploy the Worker and static assets
   (`npm run deploy`, which does not build on its own).
3. Run `POST /api/admin/backfill-e2e` with `{ "days": 7 }` to repair any rows
   written by the old Worker between migration and deploy. Admin-only; clamps
   days to 1–7; returns the updated row count.
4. Refresh the snapshot: `POST /api/admin/reaggregate` with
   `{ "refresh_snapshot": true }`.
5. Recompute hourly e2e history for the last 7 days: call
   `POST /api/admin/reaggregate` with one ISO hour per call (168 calls, off-peak).
   Ten-minute buckets are not backfilled; the 1h view fills within an hour.

### Admin route changes (`src/api/admin/maintenance.ts`)

- `POST /api/admin/reaggregate` accepts optional `{ hour?: ISO string,
  refresh_snapshot?: boolean }`. Default hour is the current UTC hour. Invalid
  or out-of-retention hours return 400. When `refresh_snapshot` is true, call
  `refreshLeaderboardSnapshot` after aggregation.
- New `POST /api/admin/backfill-e2e` accepts `{ days?: number }` (default 7,
  clamp 1–7) and runs the same formula as the migration, restricted to rows
  where `e2e_tps IS NULL`. Returns `{ ok, updated }`.
- Both require `isAdmin` and are documented in OpenAPI.

### Rollback

Revert the code. The added columns are nullable and ignored by the previous
Worker. No data is deleted. Ranking returns to decode immediately on rollback.
The only irreversible artifact is the extra storage, which is inert.

## 12. Risks and mitigations

| Risk | Mitigation |
|---|---|
| End-to-end varies with edge location and network | 7d medians; label it "measured from our Cloudflare runner"; do not claim provider-universal throughput |
| Every Overall Score shifts, rank changes look like a regression | Document in methodology and release note; keep decode visible; expected movement is the point |
| `julianday` parsing differs from JS | Verify on local seed; run both the zero-null and parse-failure checks; fall back to the JS admin backfill |
| 168-hour backfill adds D1 reads | Run off-peak, one hour per call, only once; monitor rows-read before/after |
| Stale snapshot after deploy | Explicit `refresh_snapshot` step; verify model 69 numbers before announcing |
| Compare serves a pre-deploy cached body | Bump cache key to `v=2` |
| Block badge false positives | Badge is informational and never affects numbers or rank; threshold documented |
| Leaderboard becomes too dense with two metrics in four windows | Default Both stacks two compact lines; the segmented control reduces density |
